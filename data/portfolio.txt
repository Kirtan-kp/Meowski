# Projects

## 1. Cat RAG — Retrieval-Augmented Generation Application

### Overview

Cat RAG is a Retrieval-Augmented Generation application that I am building to explore how modern RAG systems can be designed beyond a basic "embed documents → retrieve chunks → send them to an LLM" pipeline.

The project is intended to demonstrate a more complete retrieval architecture involving multiple retrieval strategies, reranking, query processing, context assembly, filtering, citations, and evaluation.

The name "Cat RAG" comes from the project's cat-themed identity, but technically the project is focused on building a robust and modular RAG system.

### Why I Built It

I wanted to understand RAG as an actual engineering system rather than treating it as simply an API call to an LLM.

A basic RAG application can retrieve a few similar chunks and pass them to a language model, but real-world retrieval introduces several problems. A relevant document may contain exact keywords that dense retrieval does not prioritize, while another relevant document may be semantically similar without sharing the same words as the query.

Because of this, I wanted to experiment with combining different retrieval approaches and adding additional stages to improve the quality of the final context.

### Retrieval Architecture

The retrieval architecture uses a hybrid approach combining dense retrieval and lexical retrieval.

Dense retrieval uses embeddings to find documents that are semantically related to a query. This is useful when the query and document express the same concept using different words.

BM25 provides lexical retrieval and is particularly useful when exact words, names, technical terminology, or specific phrases are important.

The results from these retrieval methods can be combined using Reciprocal Rank Fusion, or RRF. RRF allows results from multiple retrieval systems to be merged into a unified ranking without requiring the individual retrievers to produce directly comparable scores.

After the initial retrieval and fusion stage, a cross-encoder reranker can be used to examine query-document relevance more directly and reorder the retrieved candidates.

The overall retrieval flow can therefore be described as:

```text
User Query
    ↓
Query Processing
    ↓
Dense Retrieval ──────┐
                       ├──→ Reciprocal Rank Fusion
BM25 Retrieval ───────┘
                              ↓
                       Candidate Documents
                              ↓
                     Cross-Encoder Reranking
                              ↓
                       Context Assembly
                              ↓
                         LLM Generation
                              ↓
                       Answer + Citations
```

### Query Processing

The system can perform query rewriting and multi-query retrieval when reformulation can improve retrieval.

Instead of rewriting every query automatically, the idea is to determine when reformulation can improve retrieval. This avoids unnecessarily changing queries that are already clear and precise.

Query processing is therefore treated as part of the retrieval system rather than simply assuming that the user's original wording will always be optimal for document retrieval.

### Metadata and Access Filtering

The project also considers metadata-based filtering and session-aware retrieval.

Metadata can be used to restrict retrieval based on properties of documents, while session information can help maintain appropriate context across interactions.

This is important because a good retrieval system should not simply retrieve semantically similar documents; it should retrieve documents that are relevant and valid for the current context.

### Context Assembly and Citations

Retrieved documents are not simply passed directly to the language model.

The system assembles the relevant information into a structured context that can be used to generate a grounded answer.

Citations are also an important part of the system because they allow the generated response to point back toward the information used to construct it. This makes the result more transparent and helps distinguish retrieved information from generated language.

### Evaluation

A major goal of the project is to evaluate the retrieval system instead of judging its quality only by manually asking a few questions.

The evaluation process considers both retrieval quality and answer quality.

This is important because a language model can sometimes generate a convincing answer even when retrieval was poor. A proper RAG evaluation therefore needs to consider whether the correct information was retrieved as well as whether the final response used that information appropriately.

### What I Learned

Working on Cat RAG has helped me understand that building a useful RAG system involves considerably more than connecting an embedding model to a vector database.

It has given me practical exposure to:

- Dense retrieval
- BM25
- Hybrid search
- Reciprocal Rank Fusion
- Cross-encoder reranking
- Query rewriting
- Metadata filtering
- Session-aware retrieval
- Context assembly
- Citations
- Retrieval evaluation
- RAG architecture design

The project has also changed the way I think about AI applications. I increasingly see an AI application as a complete system involving data, retrieval, models, infrastructure, evaluation, and user interaction rather than simply a machine learning model.

# 2. Vehicle Performance & Analytics — MLOps Pipeline

## Overview

Vehicle Performance & Analytics is an end-to-end MLOps project designed to automate the machine learning lifecycle from data ingestion to model deployment.

The project was built around a modular architecture where individual components are responsible for specific stages of the pipeline. The goal was to understand how a machine learning model can be moved from an experimental environment toward a more production-oriented workflow.

The system combines MongoDB Atlas, AWS services, Docker, GitHub Actions, and a modular Python architecture to create an automated CI/CD and model delivery pipeline.

## Problem the Project Addresses

A machine learning project does not end when a model achieves good accuracy.

A production-oriented system needs to handle data ingestion, validation, transformation, training, evaluation, model versioning, deployment, logging, error handling, and continuous delivery.

This project was designed to explore those engineering problems and connect the different stages into one automated pipeline.

## System Architecture

The pipeline is divided into several independent components:

```text
MongoDB Atlas
     ↓
Data Ingestion
     ↓
Data Validation
     ↓
Data Transformation
     ↓
Model Training
     ↓
Model Evaluation
     ↓
Model Pushing
     ↓
AWS S3 Model Registry
     ↓
Dockerized Production Application
     ↓
AWS EC2
```

Each component has a specific responsibility, allowing the overall system to remain modular and easier to maintain.

### Data Ingestion

The data ingestion component retrieves the vehicle-related dataset from MongoDB Atlas and creates local data artifacts for the downstream pipeline.

MongoDB Atlas acts as the cloud-based NoSQL data source.

### Data Validation

Before the data is used for training, the pipeline validates the dataset against a predefined schema.

Schema-based validation helps ensure that the structure of incoming data remains compatible with the rest of the machine learning pipeline.

This provides an important safeguard against unexpected changes in the dataset.

### Data Transformation

The transformation stage handles preprocessing and feature engineering required before model training.

The transformation component produces processed data artifacts that can be consumed by the model-training stage.

### Model Training

The model trainer is responsible for training machine learning models using the transformed dataset.

The trained estimators are then stored as artifacts for subsequent evaluation.

### Model Evaluation

One of the important aspects of the project is that a newly trained model is not automatically considered suitable for production.

The evaluation stage compares the newly trained model against an existing production baseline stored in AWS S3.

A predefined improvement threshold is used as a gate. The project uses a minimum performance improvement threshold of 0.02 before a newly trained model is pushed as an updated production model.

This creates a basic form of automated model gatekeeping rather than deploying every newly trained model automatically.

### Model Registry

AWS S3 is used as part of the model registry workflow.

When a newly trained model satisfies the evaluation criteria, the model pusher stores the validated model in the designated S3 model registry location.

This provides a centralized location for production model artifacts.

## Cloud Infrastructure

The project uses several AWS services for different parts of the infrastructure:

### AWS S3

Used for storing model artifacts and maintaining the production model registry.

### AWS EC2

Used as the production compute environment where the application is hosted.

### AWS ECR

Used as the container registry for Docker images.

### AWS IAM

Used for managing access to AWS resources required by the pipeline.

Together, these services provide the cloud infrastructure needed for the project's model delivery workflow.

## Docker and Containerization

The production application is containerized using Docker.

Containerization helps package the application and its runtime dependencies into a consistent environment, reducing differences between development and deployment environments.

The Docker image can be built and delivered through the CI/CD workflow and deployed to the production EC2 environment.

## CI/CD with GitHub Actions

GitHub Actions is used to automate the continuous integration and continuous deployment workflow.

The project uses a self-hosted GitHub Actions runner running on the AWS infrastructure.

When changes are pushed to the repository, the CI/CD workflow can execute the required build and deployment operations, including building the Docker image and delivering the updated application.

This reduces the amount of manual work required to move changes from the development repository into the deployed environment.

## Logging and Exception Handling

The project contains centralized logging and exception-handling components to improve traceability during pipeline execution.

Instead of allowing failures to occur without context, the system records information about pipeline execution and errors.

This is particularly important in an MLOps environment because a pipeline may involve multiple independent stages, and identifying exactly where a failure occurred is essential for debugging.

## Modular Architecture

A major design principle of the project is modularity.

Components such as:

- Data Ingestion
- Data Validation
- Data Transformation
- Model Training
- Model Evaluation
- Model Pushing

are kept separate.

The project also uses configuration and artifact entities to allow different pipeline components to communicate in a structured way without tightly coupling the implementation of every component.

This makes the system easier to understand, test, modify, and extend.
